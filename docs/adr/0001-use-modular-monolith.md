# ADR-0001 采用模块化单体，而不是一开始就上微服务

- **状态**：已接受
- **日期**：2026-10-25
- **相关**：ADR-0002、ADR-0003

## 背景

项目有 13 个业务模块（身份、空间、文档、协同、搜索、通知、审计、AI 等），
目标是既能把功能做出来，又能把技术栈练到能讲清取舍的程度。

一个 3 年经验的 Java 工程师做这种项目，最容易踩的坑是：**先搭一套微服务，
然后 80% 的时间花在 Docker Compose、服务发现、跨服务联调上，业务只写了三个 CRUD。**

## 候选方案

### 方案 A：微服务（每个模块一个 Spring Boot 应用）

- 优点：听起来专业；天然支持独立部署；能练习服务治理。
- 缺点：本地要跑 10+ 个进程；一个功能改动要跨 3 个仓库/模块；没有真实流量时，
  熔断、限流、链路追踪全是「演」出来的，学不到问题的本质。

### 方案 B：单体 + 按包分层（controller/service/repository 平铺）

- 优点：最简单，上手最快。
- 缺点：半年后必然变成大泥球。没有边界约束，任何一个类都能 import 任何东西，
  「模块」只是口头约定，最终谁也不敢改。

### 方案 C：模块化单体（Modular Monolith）

- 一个部署单元，但代码内部按业务模块严格分区，模块之间只通过显式接口通信。
- 优点：部署简单（一个 jar + 几个容器）；边界可被工具强制校验；
  将来真的需要拆服务时，模块就是天然的拆分单位。
- 缺点：需要额外的纪律和工具支撑，否则退化成方案 B。

## 决定

**采用方案 C：模块化单体。**

物理结构上是一个 Maven 多模块工程，最终打包成**一个** Spring Boot 应用：

```
platform  ← 技术底座（共享内核）
identity  ← 业务模块，只允许依赖 platform
workspace ← 同上
document  ← 同上
app       ← 唯一部署单元，负责装配
```

拆分服务的时机写在需求文档里：**当某个模块有独立的扩缩容需求，或团队超过 8 人时**。
在那之前，拆服务是负债不是资产。

## 后果

### 正面

- 本地一条 `docker compose up -d` + `mvnw spring-boot:run` 就能跑起来。
- 事务是本地事务，不需要处理分布式一致性（M1~M4 都不需要）。
- 调试简单：一个断点能走完全流程。

### 代价

- 需要工具来守边界：Spring Modulith（ADR-0002）+ ArchUnit，两者都进 CI。
- 打包是单一的，某个模块的 CPU 密集操作会拖累整体（比如 M3 的协同编辑广播）。
  这正好是 M6「拆一个服务」的练习素材。
- 模块之间的调用是进程内的，将来拆出去要改成 RPC，这部分成本是预付的。

## 何时重新评估

- 单个模块需要独立扩缩容（如协同编辑的长连接数远超 HTTP 请求）
- 团队规模超过 8 人，模块间协作成本高于部署成本
- 某个模块的技术栈与整体差异过大（例如 AI 模块需要 Python 生态）

满足任意一条，就开一篇新的 ADR 讨论拆分方案。
