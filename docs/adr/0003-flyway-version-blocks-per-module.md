# ADR-0003 Flyway 迁移脚本按模块划分版本号段

- **状态**：已接受
- **日期**：2026-10-25
- **相关**：ADR-0001、ADR-0002

## 背景

模块化单体有 13 个业务模块，每个模块都要建自己的表。问题来了：
迁移脚本放在哪、版本号怎么分配？

Flyway 的版本号是**全局唯一**的，`V1`、`V2`、`V3` 一旦被某个模块占用，
其他模块就不能再用。如果所有脚本都塞在一个目录里，半年后会得到一个
300 个文件的扁平目录，没人说得清哪张表属于哪个模块。

## 候选方案

### 方案 A：所有迁移集中放 `app/src/main/resources/db/migration`，全局顺序编号

- 优点：简单，一眼看清全库的演进顺序。
- 缺点：`app` 模块成了「所有 schema 的拥有者」，与模块化单体的思想冲突；
  目录会膨胀到无法维护；两个模块同时开发时版本号必然冲突。

### 方案 B：每个模块自带迁移，版本号用时间戳（`V20261025133000__...`）

- 优点：永不冲突，天然按时间排序。
- 缺点：读不出顺序意图；两个人同一分钟提交还是会撞；版本号对人类不友好。

### 方案 C：每个模块自带迁移，按模块分配版本号段

- 优点：冲突概率为零；看版本号就知道归属；模块可以整体抽出而不带走别家的脚本。
- 缺点：需要一张「号段登记表」；号段之间有空洞（Flyway 不在乎，但有人会看着别扭）。

## 决定

**采用方案 C。**

### 号段分配

| 模块 | 号段 | 当前最高 |
|---|---|---|
| platform | V0001 – V0999 | V1 |
| identity | V1001 – V1999 | — |
| workspace | V2001 – V2999 | — |
| document | V3001 – V3999 | — |
| file | V4001 – V4999 | — |
| notification | V5001 – V5999 | — |
| audit | V6001 – V6999 | — |
| ai | V7001 – V7999 | — |
| open | V8001 – V8999 | — |
| admin | V9001 – V9999 | — |

新增模块时，在这张表里登记号段，并同步更新本节。

### 目录结构

```
platform/src/main/resources/db/migration/V1__platform_baseline.sql
identity/src/main/resources/db/migration/V1001__identity_create_user_account.sql
workspace/src/main/resources/db/migration/V2001__workspace_create_workspace.sql
```

Spring Boot 的配置只需一条（各模块的 jar 都在 classpath 上，Flyway 会自动全部扫描）：

```yaml
spring.flyway.locations: classpath:db/migration
```

## 后果

### 正面

- 版本号即归属，`V3007` 一定是 document 模块的。
- 模块将来被拆分出去时，它的表结构演进历史可以整段带走。
- 两个模块并行开发，永不撞版本号。

### 代价

- 号段是人为约定，需要维护这张表；忘记登记会撞号（Flyway 启动时会直接报错，不会静默出错）。
- 版本号不连续，`V1` 之后直接跳 `V1001`，新人会问「中间的呢」。

## 硬性规则

1. **已执行的迁移脚本永不修改**。改表结构要新增一个脚本。
   修改会导致 Flyway checksum 校验失败，而且已经上线的环境无法回滚。
2. 每个脚本只做一件事，一个脚本里不要既建表又改别的模块的表。
3. 脚本必须可重复执行到「同一个最终状态」的理解下编写 —— 但**不要**用
   `IF NOT EXISTS` 掩盖问题，构建期就该暴露冲突。
4. 生产环境禁止 `flyway clean`（配置里已设 `clean-disabled: true`）。
